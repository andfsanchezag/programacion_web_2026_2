# Global Exception Handler Specification

## 1. Purpose

This document defines the single error-handling contract for the REST delivery layer. It applies to every endpoint and middleware error, regardless of whether the detected stack is TypeScript/Express or Java/Spring Boot. Cross-stack precedence, aliases and the status policy are defined in `backendSDD/Contract-alignment.md`.

The domain remains technology independent. Domain exceptions are declared in `domain/exceptions/`; the REST/infrastructure layer translates them into HTTP responses.

## 2. Responsibilities

The global handler must:

1. Capture errors from controllers, routes, authentication middleware, authorization middleware, validation, persistence adapters and unexpected runtime failures.
2. Map known exceptions deterministically to an HTTP status.
3. Return one stable error response shape.
4. Avoid exposing stack traces, SQL details, secrets or internal implementation data in production responses.
5. Log unexpected errors with a correlation/request identifier.
6. Preserve the original exception for diagnostics and tests.
7. Respect `res.headersSent` or the equivalent framework rule and delegate safely when a response has already started.

No controller should duplicate the complete exception-to-HTTP mapping. Local catches are allowed only to add context or to rethrow into the global handler.

## 3. Standard Error Response

All handled errors must use this shape, unless the API contract explicitly requires another representation:

```json
{
  "timestamp": "2026-09-23T12:00:00.000Z",
  "status": 404,
  "code": "CUSTOMER_NOT_FOUND",
  "message": "Customer not found",
  "path": "/api/v1/customers/1017",
  "requestId": "req-01H...",
  "details": null
}
```

Rules:

- `timestamp` is generated by the handler.
- `status` is the HTTP status actually returned.
- `code` is stable and machine-readable; clients must not parse `message`.
- `message` is safe for the client.
- `path` identifies the request path without query secrets.
- `requestId` correlates the response with server logs.
- `details` contains safe validation details or is `null`.
- Unexpected errors use a generic message such as `Internal server error`.

## 4. Exception Classification

The mapping must be explicit and covered by tests:

| Exception category | HTTP status | Example code |
|---|---:|---|
| Malformed JSON, missing/invalid request data | 400 | `INVALID_REQUEST` |
| Domain validation or semantic validation failure | 400 by default; 422 only when explicitly declared by an endpoint contract | `INVALID_DOMAIN_VALUE` |
| Missing or invalid credentials/token | 401 | `AUTHENTICATION_REQUIRED`, `INVALID_CREDENTIALS` |
| Authenticated user without permission | 403 | `FORBIDDEN` |
| Resource does not exist | 404 | `RESOURCE_NOT_FOUND` |
| Duplicate resource or state conflict | 409 | `RESOURCE_ALREADY_EXISTS`, `INVALID_STATE_TRANSITION` |
| Persistence/service dependency unavailable | 503 | `DEPENDENCY_UNAVAILABLE` |
| Unexpected programming/runtime error | 500 | `INTERNAL_ERROR` |

The implementation must not use a broad fallback that maps every unknown error to `400`. Unknown errors are server errors and must map to `500`. This project uses `400` for request validation and `409` for business conflicts unless `Api-rest-endpoints.md` explicitly declares `422`.

## 5. Domain Exception Contract

Each domain exception must have:

- a stable exception class;
- a stable external error code;
- a safe default message;
- an explicit classification or a central registry entry;
- no dependency on Express, Spring, HTTP, ORM or database classes.

If the current domain exceptions only expose `name` and `message`, the adapter may maintain a central mapping registry, but the mapping must be deterministic and tested.

## 6. Framework Implementations

### 6.1 TypeScript / Express

Implement an Express error middleware with the signature:

```ts
(error: unknown, req: Request, res: Response, next: NextFunction) => void
```

Requirements:

- register it after all routes and ordinary middleware;
- use `next` when headers have already been sent;
- handle rejected async handlers through the framework-compatible wrapper or explicit propagation;
- assign or reuse a request ID;
- never send two responses for one request;
- return the standard error response;
- log stack traces only on the server side.

### 6.2 Java / Spring Boot

Implement a global `@RestControllerAdvice` with `@ExceptionHandler` methods or an equivalent centralized resolver.

Requirements:

- handle domain exceptions, validation exceptions, authentication/authorization exceptions, persistence failures and a final unexpected-error handler;
- return the standard error response DTO;
- preserve request ID and path;
- avoid leaking stack traces in the response;
- use the project logging framework for internal diagnostics.

## 7. Endpoint Contract Integration

`backendSDD/Adapters/Api-rest-endpoints.md` is the source of truth for endpoint methods, paths, request/response DTOs and expected HTTP statuses. Each endpoint must document, or be traceable to, its possible error codes.

The implementation must verify that:

1. every documented endpoint reaches the global handler on failure;
2. status codes match both the endpoint contract and this classification;
3. authentication and authorization failures are not converted to generic `400` errors;
4. persistence failures are not exposed as raw database errors;
5. successful responses are not changed into error responses after headers are sent.

## 8. Required Tests

At minimum, provide tests for:

- malformed JSON and invalid DTO;
- invalid domain value;
- invalid credentials and missing token;
- forbidden role;
- not-found exception;
- duplicate/conflict exception;
- persistence/dependency failure;
- unexpected exception resulting in `500`;
- stable response shape and error code;
- request ID propagation;
- no duplicate response when headers were already sent;
- every documented endpoint's principal error cases.

Unit tests may mock dependencies. Integration or REST tests must verify the actual middleware/advice registration and serialized HTTP response.

## 9. Acceptance Gate

The Global Exception Handler is `VERIFIED` only when:

- this contract is implemented for the detected stack;
- the handler is registered globally after routes or through the framework equivalent;
- all exception categories have deterministic mappings;
- unknown errors return `500` without internal details;
- tests pass for all required categories;
- endpoint documentation and implementation agree;
- build, unit tests and integration/REST tests pass with recorded commands and exit codes.

Until all conditions pass, the orchestrator must mark this deliverable `PARTIAL` or `FAILING`, never `VERIFIED` or `COMPLETE`.
